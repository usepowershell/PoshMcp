# PoshMcp v0.15.1 Release Notes

**Release Date:** May 20, 2026

## Summary

Patch follow-up to v0.15.0 tightening noun-derived resource eligibility, adding explicit per-command associated resource links, and fixing doctor/config-status noun-resource parity so diagnostics reflect the same effective registry the runtime uses.

## What's Changed

### Noun-resource eligibility tightening (PR #292)

Noun-derived resources are now registered only when the matching `Get-{Noun}` command has at least one parameter set that can run without required user parameters.

This keeps all noun-resource surfaces aligned with what the runtime can actually read:

- `resources/list` no longer advertises unreadable derived resources
- `resources/read` no longer implies support for `Get-*` commands that always need user input
- successful sibling tool calls no longer get noun-resource link blocks for those non-resourceable nouns

### Explicit `AssociatedResourceUri` command override links

Per-command overrides can now set `AssociatedResourceUri` to link successful tool results to an explicitly chosen MCP resource instead of relying only on the implicit noun-derived link.

Key behavior:

- the setting lives on `PowerShellConfiguration.CommandOverrides` with legacy `FunctionOverrides` binding preserved
- the explicit URI resolves against the exposed resource surface at tool-registration time
- static/custom resources are checked first, then noun-derived resources when noun resources are enabled
- if the configured URI does not resolve, PoshMcp logs a warning and falls back to the implicit noun-derived link when available
- explicit associated links are appended even when `DisableResourceLinkBlock` suppresses the implicit noun-derived link

This makes it possible to point a command at a specific context resource, including when noun resources are disabled.

### Doctor and configuration-status noun-resource parity fix

`poshmcp doctor` and the runtime `get-configuration-status` surface now reuse the same eligibility-aware noun registry captured during discovery.

That means diagnostic output now matches the effective runtime noun-resource surface for:

- required-parameter `Get-*` commands that are no longer resourceable
- override-adjusted names and URIs
- suppressed nouns and registered resources shown in doctor/config-status output

## Documentation

- Updated the configuration guide with `AssociatedResourceUri` behavior and precedence details
- Updated the resources guide with explicit associated-resource link behavior and fallback rules

## Tests

- Added integration coverage for explicit associated-resource links, including static-resource links when noun resources are disabled
- Added unit and functional coverage for eligibility-aware noun-resource parity in doctor and configuration-status output
- Added regression coverage for required-parameter `Get-*` commands so list/read/link behavior stays aligned

## Breaking Changes

None.

## Upgrade Notes

**Drop-in upgrade.** No configuration changes are required.

If you already enabled noun-derived resources in v0.15.0, expect some previously advertised nouns to disappear from `resources/list` when their backing `Get-*` commands cannot be invoked without required user parameters. If you want a command to link to a specific resource regardless of noun-derived behavior, set `AssociatedResourceUri` on that command override.
