# PoshMcp v0.13.0 Release Notes

**Release Date:** May 14, 2026

## Summary

Spec 010 lands. MCP tool descriptions and per-parameter descriptions are now sourced from PowerShell `Get-Help` and `CommandInfo` metadata, with a documented FR-500 / FR-510 precedence chain and FR-540 sanitization. The in-process and out-of-process execution paths now produce **byte-identical** `tools/list` output for the same command — no more "raw syntax line in-process, synopsis-only out-of-process" split. The release also adds OTel counters and `doctor` reporting for description resolution, locks in pre/post-spec010 cold-start benchmark gates, and fixes a long-standing `SwitchParameter` round-trip bug.

## What's New

### Help-aware tool descriptions (spec 010)

PoshMcp now reads what tool authors actually wrote. For each command exposed as an MCP tool, the server consults `Get-Help` and `CommandInfo` and resolves a description through the FR-500 (command) and FR-510 (parameter) precedence chains, with FR-540 sanitization applied to the resolved strings.

**Before:**

| Path | Tool description for `Get-AzContext` | `-Name` parameter description |
|------|--------------------------------------|-------------------------------|
| In-process | `Get-AzContext [[-Name] <string>] [-DefaultProfile <IAzureContextContainer>]` (raw syntax) | `Parameter of type String` |
| Out-of-process | `Gets the metadata used to authenticate Azure Resource Manager requests.` (Synopsis only) | `Parameter of type String` |

**After (both paths, byte-identical):**

| Tool description | `-Name` parameter description |
|------------------|-------------------------------|
| `Gets the metadata used to authenticate Azure Resource Manager requests.` | `The name of the context.` |

No author action is required — if your function or cmdlet has comment-based help, MAML, or external XML help, MCP clients will see it. The exposing-tools guide documents the full precedence chains and how to author help that resolves the way you expect.

### `IToolMetadataSource` seam

The metadata pipeline is now built around an `IToolMetadataSource` abstraction (#238). The default in-process implementation, `HelpAwareToolMetadataSource`, is the new default in `PowerShellSchemaGenerator` (#250). The OOP path implements the same seam (#241), and `RemoteToolSchema` was extended to carry the full description plus per-parameter metadata across the subprocess boundary (#239).

This is the foundation for any future metadata source — alternate help providers, declarative overlays, or test doubles plug in here without touching the schema generator.

### `doctor` reports resolved description source

`poshmcp doctor` now reports the resolved `descriptionSource` per command and per parameter (#244). For each tool, you can see whether the description came from `HelpSynopsis`, `HelpDescription`, `HelpMessage`, `ParameterSetSyntax`, or fell through to a fallback. This is the fastest way to debug "why is my tool description still the syntax line?" — the source is right there in the doctor report.

### OTel metrics for description-source resolution

A new set of OpenTelemetry counters emits resolution outcomes (#245). For each command and parameter description resolved during tool list generation, a counter increments tagged with the resolved source. Operators running PoshMcp at scale can now answer "how many of our exposed tools are falling back to the syntax line vs. resolving from real help?" from their telemetry pipeline instead of by inspection.

### Parity, regression, and parameter-set tests

A new test suite (#243) locks in three guarantees:

- **Parity:** the in-process and out-of-process paths return byte-identical descriptions for the same command.
- **Regression:** known-good descriptions resolved from `Get-Help` cannot silently revert to the syntax-line fallback.
- **Parameter-set consistency:** description resolution behaves consistently across multiple parameter sets on the same command.

### Pre/post-spec010 cold-start benchmark gates

The benchmarks harness captured a pre-spec010 cold-start baseline (#237) and a post-spec010 cold-start measurement (#246). The post-spec010 run is gated to fail on greater than 50% cold-start regression versus run-5. Reading more help during tool listing is not free, but the cost is now bounded and observable.

## Bug Fixes

### `SwitchParameter` round-trips through MCP JSON arguments (#222)

A boolean argument bound to a PowerShell `SwitchParameter` did not round-trip cleanly through MCP JSON tool arguments. Switches that callers passed as `true` could fail to bind, or bind as a literal value rather than as a present/absent switch. The argument-binding path now correctly handles the `SwitchParameter` shape on both code paths.

### Parameter descriptions wired through to MCP `inputSchema` (#248)

Per-parameter descriptions resolved by the metadata source were not consistently reaching the MCP `inputSchema` payload — the resolver did the work, but the schema generator did not consume it. This is now wired end-to-end so the descriptions resolved from help land in the JSON Schema clients see.

### `HelpAwareToolMetadataSource` is the default in `PowerShellSchemaGenerator` (#250)

`PowerShellSchemaGenerator` defaulted to a fallback metadata source instead of the help-aware one in some construction paths, which meant the in-process flow could still emit syntax-line descriptions even with the new seam in place. The default is now `HelpAwareToolMetadataSource` everywhere `PowerShellSchemaGenerator` is constructed without an explicit source.

## Documentation

- **Exposing tools — precedence chains (#247):** the exposing-tools guide now documents the FR-500 (command description) and FR-510 (parameter description) precedence chains end-to-end, including FR-540 sanitization, with worked examples for each fallback step.
- **`RemoteToolSchema` XML doc (#235):** the previous XML doc on `RemoteToolSchema.Description` claimed it was sourced from `Get-Help` or parameter set syntax. Neither was true before spec 010, and both fields' real semantics are now documented accurately for the new world.

## Tests & Benchmarks

- Pre-spec010 `tools/list` snapshots captured (#236) for regression comparison.
- Pre-spec010 cold-start baseline captured (#237).
- Tool description parity, regression, and parameter-set consistency tests added (#243).
- Post-spec010 cold-start measurement, gated at <50% regression vs run-5 (#246).

## Breaking Changes

None.

This is a behavior change for any tool whose description was previously the raw parameter set syntax line. Clients that displayed that string verbatim will now display the help-derived description instead. The MCP protocol surface, configuration schema, and CLI are unchanged.

## Upgrade Notes

**Drop-in upgrade.** No configuration changes required.

- **Binary / direct install:** Replace the build, restart the server.
- **Container users:** Rebuild your derived image from `poshmcp:latest` (or pull the updated tag). No changes to `appsettings.json`, `Dockerfile`, or startup script are required.

After upgrading, run `poshmcp doctor` to confirm the resolved `descriptionSource` for each exposed command and parameter. If a tool you expected to have a real description still shows the syntax-line fallback, the doctor report will tell you which step of the precedence chain produced the result, and the exposing-tools guide explains how to add help that resolves the way you want.
