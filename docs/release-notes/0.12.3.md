# Release v0.12.3

**Release Date:** May 12, 2026

## Summary

Hotfix. Closes a correctness bug in the out-of-process executor where a PowerShell command that produced intermediate pipeline output and then wrote a non-terminating error would return the partial output to the MCP client as if the call had succeeded. Callers saw what looked like stale or cached output from prior tools. Validated in production against the original repro (`Assert-BamiTenantRoleMember`).

## Fixes

### Errors no longer return partial output as success (`6908917`)

**Symptom:** A tool invocation that internally emitted pipeline output and then wrote a non-terminating error (`Write-Error`, or a cmdlet that did the same) returned the partial output to the MCP client as a successful tool result. The executor logged `hadErrors=true`, but the result frame still carried the intermediate objects. To clients this looked like the previous tool's output leaking into the next call.

**Real-world example:** `Assert-BamiTenantRoleMember` resolves a tenant context (emitting the context object) before validating the role assignment. When the role check failed in v0.12.2, the tenant-context object was returned as the tool result instead of the role-check error.

**Root cause:** Both `OutOfProcessCommandExecutor` and the pool executor inspected `hadErrors` only for logging. When `hadErrors=true && !cancelled`, the executor still serialized whatever was on the success pipeline and returned it.

**Fix:** When `hadErrors=true && !cancelled`, the executor now throws `InvalidOperationException` with an `"OOP error:"` prefix, which MCP surfaces as a proper tool error. Cancellation path is unchanged — cancelled invocations still return the cancellation signal, not an error.

Applies to both the single-host executor and the pool executor.

### Per-invoke scope for user script (`e1c923e`)

Belt-and-suspenders. `oop-host.ps1` and `oop-host-pool.ps1` now invoke user script with `useLocalScope=$true`. The per-invoke working variable (`$r`) lives in a child scope that's discarded when the pipeline returns, instead of the runspace's default scope where a future invoke on a leased runspace could theoretically observe it. No reproducer was found for cross-invoke leakage at the host level, but the scope discipline is correct and cheap.

## Behavior notes

**This is a behavior change for any tool that wrote non-terminating errors but also produced pipeline output.**

- v0.12.2: that call returned the pipeline output to the client; the error was logged server-side only.
- v0.12.3: that call returns an error to the client. The pipeline output is not surfaced.

If you have callers that were relying on the old behavior (reading the partial output and ignoring the logged error), they will now see a tool error instead. The new behavior is the correct one — silent partial success was the bug.

Cancellation semantics are unchanged.

## Tests

Added under `Category=OutOfProcess` (`d7a3644` and follow-ups):

- Cross-invoke output leak regression tests covering both the single-host and pool-host paths.
- Pool-host tests use a production-shape configuration (multiple slots, real `SetupAsync` replay) so the regression is exercised on the path users actually run.

All 47 `Category=OutOfProcess` tests pass.

## Upgrade path

Drop-in patch. No configuration changes.

- **Binary / direct install:** Replace the build, restart the server.
- **Container users:** Rebuild your derived image from `poshmcp:latest` (or pull the updated tag). No changes to `appsettings.json`, `Dockerfile`, or startup script are required.

Review any callers that consumed partial output from tools that also wrote non-terminating errors. They will now receive a tool error.
