# PoshMcp v0.11.0 Release Notes

This release matures out-of-process (OOP) PowerShell execution into the recommended path for production MCP workloads. The default subprocess topology is now a runspace **Pool**, a new **ProcessPool** topology lands for trust-boundary and tail-latency-sensitive deployments, request cancellation now propagates across the OOP boundary, and a new benchmarks harness backs the default change with reproducible numbers.

## What's New

### OOP execution: `Pool` is now the default `SubprocessHostMode`

When `RuntimeMode` is `OutOfProcess`, `SubprocessHostMode` selects the subprocess topology. As of v0.11.0, the default is `Pool` — a single subprocess host with an internal runspace pool — replacing the previous `Single` default.

Available modes:

| `SubprocessHostMode` | Topology | When to use |
| -------------------- | -------- | ----------- |
| `Single` | One subprocess, one runspace | Lowest-resource footprint; legacy / single-user scenarios. |
| `Pool` (default) | One subprocess, runspace pool inside it | Best concurrent warm-invoke throughput; recommended for typical MCP workloads. |
| `ProcessPool` | N independent single-runspace subprocess hosts, leased per request | Trust-boundary or tail-latency-sensitive workloads. Crashes are reconciled per slot without disturbing other hosts. |

The default flip is driven by benchmark data — `Pool` posted ~4.86× warm-invoke throughput at concurrency 10 versus `Single` in the v0.11.0 benchmark study. See `specs/004-out-of-process-execution/benchmark-findings.md` for the full report.

**Pool sizing** is controlled by:

- `SubprocessRunspacePoolSize` (Pool mode) — runspaces in the pool. `0` (default) auto-sizes to `min(ProcessorCount, 8)`. Ignored in `Single` and `ProcessPool` modes.
- `SubprocessPoolSize` (ProcessPool mode) — independent subprocess hosts to launch. Default `4`.
- `SubprocessMinHealthyForStartup` (ProcessPool mode) — minimum healthy hosts required for the pool to start. Clamped to `[1, SubprocessPoolSize]`. Default `1`.

`poshmcp doctor` reports the resolved host mode, effective pool sizes, host-script path, and any clamp warnings under Runtime Settings.

See [Advanced Configuration → Out-of-Process Execution](../articles/advanced.md) for full guidance, ProcessPool examples, and tuning.

### New `ProcessPool` topology for tenant isolation and tail-latency control

`ProcessPool` runs N independent single-runspace subprocess hosts behind a leasing dispatcher. Each request leases an idle host, runs against it, and returns it to the pool when finished. Hosts that crash, time out, or report fatal errors are killed and replaced without disturbing other in-flight work.

This is the recommended topology when:

- Different invocations should not share runspace state (multi-tenant workloads, untrusted scripts).
- A misbehaving cmdlet must not be able to wedge or destabilize the entire host process.
- You need predictable tail latency under partial failure — a single bad request takes down one slot, not the whole pool.

### Cancellation propagates across the out-of-process boundary

MCP request cancellation now flows from the client through the OOP host to the running PowerShell pipeline:

- **`Pool`:** the in-process pool dispatcher locates the active `[powershell]` instance by request id and calls `BeginStop`. The runspace returns to the pool once the pipeline unwinds, so pool capacity recovers without a host restart.
- **`ProcessPool`:** each leased host inherits the same soft-cancel path. If the host honors `BeginStop`, the slot stays healthy and is returned to the pool; other hosts are unaffected. The per-request kill-on-timeout path in the subprocess pool remains as a backstop for wedged hosts (for example, a cmdlet stuck in unmanaged code) that do not honor `BeginStop` within the per-request timeout.

Cancellation is now a first-class part of the OOP contract instead of a best-effort behavior at the transport layer.

### New benchmarks harness: `PoshMcp.Benchmarks`

A new BenchmarkDotNet-based project — `PoshMcp.Benchmarks` — provides reproducible cold-start, payload-size serialization, and warm-invoke throughput scenarios across the three host modes. The harness is what informed the `Pool` default and is the canonical place to validate future changes to the OOP execution path.

See `PoshMcp.Benchmarks/README.md` for how to run the suite and interpret results.

## Security

- **Log sanitization for OOP host call sites.** All log call sites in the out-of-process host that consume attacker-controllable values — MCP method names, subprocess stdout/stderr, and echoed request ids — now route through `LogSanitizer.Scrub()` to mitigate CWE-117 (log injection / forging).
- **Minimum-permission GitHub Actions workflows.** All workflows now declare explicit, minimum required `permissions:` blocks rather than inheriting broad defaults.
- **Published security policy.** A `SECURITY.md` policy document now describes supported versions and the private vulnerability reporting process.

## Bug Fixes

- **`ConvertTo-Json` no longer silently drops a function's `Content` property** when the result object also exposes a `Length` property under PSObject's "shadowed" property semantics. Affected JSON-shaped tool output that included a `Content` field has been corrected.
- **`$Error` is now cleared before each invocation** in the OOP host, so terminating errors from a previous request can no longer be misattributed to the current one.

## Out-of-Process Execution: Spec & Documentation

- Spec **004 (Out-of-Process Execution)** documents the full `SubprocessHostMode` taxonomy, the rationale for the `Pool` default, and the runspace-pool experiment plan.
- The configuration and advanced-configuration articles under `docs/articles/` have been updated to cover `RuntimeMode`, `SubprocessHostMode`, pool-sizing knobs, and the cancellation contract.

## Upgrade Notes

**Default behavior change (`SubprocessHostMode`).** Existing deployments that ran with `RuntimeMode: OutOfProcess` and did not set `SubprocessHostMode` previously used `Single` and now use `Pool`. For most workloads this is a strict improvement (higher concurrent throughput, equal or lower tail latency under load). However, if your scripts implicitly relied on per-request runspace isolation — for example, mutating `$global:` state, leaving session-scoped variables behind, or dot-sourcing files into the active runspace — you may observe behavior differences across requests now that requests share runspaces in a pool.

**To opt out and preserve the previous default**, set `SubprocessHostMode` explicitly in your `appsettings.json`:

```jsonc
{
  "PowerShellConfiguration": {
    "RuntimeMode": "OutOfProcess",
    "SubprocessHostMode": "Single"
  }
}
```

**To opt in to per-request process isolation** (recommended for multi-tenant or untrusted-script scenarios), use `ProcessPool`:

```jsonc
{
  "PowerShellConfiguration": {
    "RuntimeMode": "OutOfProcess",
    "SubprocessHostMode": "ProcessPool",
    "SubprocessPoolSize": 4,
    "SubprocessMinHealthyForStartup": 1
  }
}
```

Run `poshmcp doctor` after upgrading to confirm the resolved host mode and effective pool sizes.

There are no breaking changes to the MCP protocol surface, configuration schema, or CLI.
