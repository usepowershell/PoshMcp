# PoshMcp v0.19.0 Release Notes

**Release Date:** 2026-08-07

## Summary

v0.19.0 upgrades the MCP SDK to **2.0.0**, switches the HTTP transport default to **Stateless**,
and replaces per-session runspace affinity with a shared warm worker pool. Each HTTP tool call
now leases a clean, reset worker from the `StatelessRunspacePool`, executes, and returns the
worker for reuse. Cross-call PowerShell state is no longer preserved over HTTP — this is a
**breaking change** for deployments that relied on side effects persisting between tool calls.

Stdio mode is unchanged: it retains a single process-scoped runspace and preserves full
PowerShell state across all calls within the process lifetime.

Release-blocking soak non-handle gates and the SDK v2 warm-call/throughput gate
([#380](https://github.com/usepowershell/PoshMcp/issues/380)) are green. Final release docs
verification: [#360](https://github.com/usepowershell/PoshMcp/issues/360).

## What's Changed

### MCP SDK 2.0.0

- `ModelContextProtocol` and `ModelContextProtocol.AspNetCore` updated from **1.4.1** to **2.0.0**.
- SDK v2 introduces the `server/discover` capability using the **`2026-07-28`** MCP protocol
  spec. Standard `initialize` continues to negotiate **`2025-11-25`**; **`2024-11-05`** remains
  supported as a compatibility fallback. The `2026-07-28` date applies only to `server/discover`
  — ordinary `initialize` handshakes are unaffected.

### HTTP transport: Stateless default

HTTP now defaults to `Stateless` mode (`McpServer:HttpTransportMode = Stateless`). Each tool call:

1. Acquires a clean worker from the shared `StatelessRunspacePool`.
2. Resets the worker to a known-clean state before executing the command.
3. Returns the worker to the pool after the call completes.

`Mcp-Session-Id` continues to control MCP protocol/session lifecycle (event sequencing, stream
lifetime) but is **not** used to route calls to a specific PowerShell worker. No per-session or
per-user runspace affinity exists in Stateless mode.

### Explicit Stateful HTTP (compatibility mode)

Setting `McpServer:HttpTransportMode = Stateful` retains MCP protocol-session semantics for
clients that require `Mcp-Session-Id` continuity. **This mode does not preserve PowerShell
execution state.** Both Stateless and Stateful modes use the same `StatelessRunspacePool` and
provide identical per-call isolation.

`IdleSessionTimeoutSeconds` applies only in Stateful mode.

### Shared warm runspace pool

The `StatelessRunspacePool` maintains a configurable set of pre-warmed, reset-ready workers.
Configure it under `McpServer:RunspacePool`:

| Key | Default | Description |
|-----|---------|-------------|
| `MaxPoolSize` | `16` | Maximum concurrent workers |
| `MinPoolSize` | `2` | Minimum workers kept warm |
| `EagerWarmCount` | `2` | Workers pre-created at startup |
| `IdleTtl` | `00:05:00` | Maximum idle time before eviction |
| `SweepInterval` | `00:00:30` | Interval between idle sweeps |
| `AcquisitionTimeout` | `00:00:15` | Maximum wait for a free worker |
| `StopTimeout` | `00:00:05` | Time to wait for graceful worker stop |
| `ShutdownDrainTimeout` | `00:00:30` | Time to drain in-flight leases on shutdown |
| `ReplenishCheckInterval` | `00:00:05` | Interval between replenishment checks |

### Startup scripts: once per warm worker

Startup scripts now run **once per warm worker** during pool initialisation — not once per process
and not once per tool call. Workers may be created concurrently during eager warm-up or pool
replenishment. Scripts must be **idempotent, deterministic, and thread-safe**. See the
[startup-script guide](../articles/startup-scripts.md).

### Health, readiness, and metrics

- **`/health`** — includes `runspace_pool` health check reporting pool state and depth.
- **`/health/ready`** — tagged `ready`; reflects pool readiness after eager warm-up completes.
  Allow the pool to reach ready state before routing production traffic.
- **Metrics** — pool depth, lease latency, reset duration, and eviction counts are now exposed.

### Configuration key: `CommandNames`

`CommandNames` is the canonical key for declaring PowerShell commands. `FunctionNames` is still
accepted with a deprecation warning and will be removed in a future major version.

### Deprecated

- **`SessionRunspace*` configuration keys** — `SessionRunspaceCapacity`,
  `SessionRunspaceWarmStandbyCount`, `SessionRunspaceIdleTtlSeconds`,
  `SessionRunspaceSweepIntervalSeconds`, and `SessionRunspaceAcquisitionTimeoutSeconds` are
  translated to their `McpServer:RunspacePool:*` equivalents at startup with a `LogWarning` per
  key used. Migrate to current keys to silence warnings (see table in [Upgrade Notes](#upgrade-notes)).
- **`SessionAwarePowerShellRunspace` and `SessionRunspaceOptions` public types** — deprecated
  compatibility surfaces; retained until the next major version.
- **HTTP-with-SSE transport** — available only via `McpServer:EnableLegacySse`; not recommended
  for new deployments.
- **Tasks extension** — deferred; not shipped in this release.

- Added [Migration guide: v1 → v2](../articles/migration-v1-v2.md) covering pool configuration,
  startup scripts, and cross-call state migration.

## Breaking Changes

### HTTP cross-call PowerShell state is no longer preserved

Stateless HTTP does not retain PowerShell variables, modules, or working directory between tool
calls. Each call starts with a clean, reset worker from the shared pool.

**Affected workflows:**

- Scripts that set `$env:` variables, call `Set-Location`, or `Import-Module` on one request and
  rely on those side effects in a subsequent request.
- Any workflow that assumed the same PowerShell session handles consecutive HTTP tool calls.

**Alternatives:**

- Pass all required state as explicit tool arguments on every call.
- Use **stdio transport** for single-client scenarios that require process-scoped PowerShell state.
- Store durable cross-call state in an external system (database, file, Key Vault) keyed by
  authenticated identity or application key.
- Set `McpServer:HttpTransportMode = Stateful` for MCP protocol-session continuity only — this
  does **not** restore PowerShell execution state.

**Rollback:** Restoring per-session runspace affinity requires reverting to the previous code and
package versions. No configuration flag re-enables the v0.18.0 per-session runspace behaviour in
v0.19.0.

### Worker affinity removed

`Mcp-Session-Id` no longer routes requests to a specific PowerShell worker. Clients that used
session IDs to maintain PowerShell state across calls must adopt one of the alternatives above.

## Known Limitations

**Residual Windows FullMix handle-floor slope** — A gradual handle-count increase was observed on
Windows hosted runners during extended soak. This was assessed as non-blocking for the migration
and is tracked in [#396](https://github.com/usepowershell/PoshMcp/issues/396). It does not affect
stateless HTTP correctness, pool isolation, or functional behaviour.

## Upgrade Notes

1. **Audit cross-call state.** Review any tool sequences that rely on PowerShell variables,
   modules, or working directory persisting between HTTP calls. Refactor before upgrading.
2. **Migrate configuration keys.** Replace `SessionRunspace*` keys with `McpServer:RunspacePool:*`
   equivalents:

   | Deprecated key (v0.18.0) | Current key | Notes |
   |--------------------------|-------------|-------|
   | `SessionRunspaceCapacity` | `McpServer:RunspacePool:MaxPoolSize` | integer |
   | `SessionRunspaceWarmStandbyCount` | `McpServer:RunspacePool:MinPoolSize` **and** `EagerWarmCount` | dual-mapped |
   | `SessionRunspaceIdleTtlSeconds` | `McpServer:RunspacePool:IdleTtl` | int seconds → TimeSpan |
   | `SessionRunspaceSweepIntervalSeconds` | `McpServer:RunspacePool:SweepInterval` | int seconds → TimeSpan |
   | `SessionRunspaceAcquisitionTimeoutSeconds` | `McpServer:RunspacePool:AcquisitionTimeout` | int seconds → TimeSpan |

   See the [migration guide](../articles/migration-v1-v2.md) for a complete mapping.

3. **Update startup scripts.** Ensure scripts are idempotent and do not assume per-session or
   per-process execution context. See the [startup-script guide](../articles/startup-scripts.md).
4. **Verify health endpoints.** Use `/health/ready` to confirm the warm pool is ready before
   routing production traffic.
5. **Rename `FunctionNames` to `CommandNames`.** The legacy key is accepted with a warning but
   will be removed in a future major version.
6. **MCP client compatibility.** Clients using standard `initialize` are unaffected. The
   `2026-07-28` protocol spec applies only to the new `server/discover` capability; existing
   `2025-11-25` and `2024-11-05` clients work without changes.

For the full scope, rollback instructions, and additional context see the
[SDK v2 upgrade notes](sdk-v2-upgrade.md).
